| 축 | 재는 것 | 값 |
| --- | --- | --- |

**이해 상태를 올리는 방법** — AI가 설명하고 내가 "그렇구나" 하는 방식으로는 안 올라간다. 뒤집어서 **내가 먼저 설명하고 AI가 코드로 대조**해야 한다. 규칙 셋: ① 말로 얼버무릴 수 있는 답은 불통과, 숫자로 답해야 통과 ② 막히면 막힌 지점을 그대로 말한다 ③ 모르면 모른다고 하고 넘어가도 된다.

## 0-A. 커널(필터)이란 무엇인가

**답변** — 커널은 모델이 사용하는 하나의 필터다. 입력 데이터에 가져다 대서 쓴다.

**교정된 부분** — 처음엔 "어떤 이미지인지 판별하는 필터"로 이해했는데, 커널 한 장은 **판별하지 않는다.** "내가 찾는 이 패턴이 여기 있나?"에만 답한다. 판별은 맨 끝 `logits` Dense가 한다.

실제 `Conv1` 0번 커널의 R채널 숫자:

```
[[-0.1717 -0.2873 -0.0713]
 [ 0.2852  0.3873  0.1753]      ← 가운데 행만 양수
 [-0.0997  0.0053 -0.0905]]
```

가운데 행이 양수, 위아래가 음수다. 이런 커널은 **가로로 뻗은 밝은 줄**에 크게 반응하고 균일한 면에서는 0에 가까운 값을 낸다. 고양이인지 얼굴인지는 모른다.

**용어** — 커널 = 필터 = 마스크. 셋 다 같은 것을 부르는 이름이다. `kernel`은 딥러닝 정식 용어(`get_weights()[0]`), `mask`는 고전 영상처리 용어, `filter`는 신호처리 유래. Keras에서 `filters` 인자는 개수를 뜻한다.

**근거 상태** — `확인됨`. 커널 값은 `keras.applications.MobileNetV2(weights='imagenet')`에서 직접 출력.

**이해 상태** — `설명가능`.

## 0-B. 커널 shape 네 자리

**답변** — `Conv1`의 커널은 `(3, 3, 3, 32)`.

```
 3    3    3    32
 │    │    │    └── 커널 장수  = 출력 채널 수
 │    │    └────── 입력 채널 수 (RGB니까 3)
 └────┴─────────── 창 크기 (3×3 = 9칸)
```

앞의 셋을 곱한 `3×3×3 = 27`이 커널 한 장의 숫자 개수다. 32장이니 `27 × 32 = 864`, 이것이 `Conv1`의 파라미터 수와 정확히 일치한다.

**규칙** — 마지막 숫자가 곧 출력 채널 수다. 그래서 `112×112×32`의 32는 커널 장수 32에서 그대로 온다. 32는 MobileNetV2 논문이 정한 설계값이다.

**§8과의 연결** — `sum`/`mean` 축소는 **3번째 자리에서만** 일어난다. 코드가 문자 그대로 그렇게 되어 있다:

```python
# tf_model.py:36-38
transferred_kernel = kernel.mean(axis=2, keepdims=True)   # mean
transferred_kernel = kernel.sum(axis=2,  keepdims=True)   # sum
```

`axis=2`는 0부터 세는 축 번호라 3번째 자리다. `(3,3,3,32)` → `(3,3,1,32)`. **커널 장수(4번째)는 안 변한다** — RGB를 IR로 바꿔도 "32가지 패턴을 찾겠다"는 설계는 그대로이기 때문이다. 파라미터는 864 → 288로 줄고, 차이 **576**이 IR 백본이 RGB 백본보다 정확히 적은 파라미터 수다.

**근거 상태** — `확인됨`. `tf_model.py:33-38`, 실측 커널 shape.

**이해 상태** — `설명가능`. 3번째 자리와 `1`을 스스로 맞힘.

## 0-C. 패치와 stride

**패치** — 커널이 덮고 있는 현재 입력 데이터의 일부분. 커널이 3×3이면 패치도 3×3이고, 모든 채널을 포함하므로 `3×3×3 = 27`개 숫자다. 코드로는 `x[0, 2:5, 2:5, :]`.

패치는 하나가 아니라 **위치마다 새로 생긴다.** stride 2로 224×224를 훑으면 패치가 112×112 = **12,544개** 만들어지고, 매 패치마다 커널 32장을 다 대므로 총 **401,408번**의 27개 곱셈-덧셈이 일어난다. `Conv1` 한 층이 하는 일이 이것 전부다.

**stride** — 커널이 한 번 패치를 찍어내는 연산이 너무 많을 수 있으니 적당히 건너뛰면서 작업하는 것. 몇 칸씩 건너뛰며 미끄러뜨리는가를 정한다.

```
입력:  [ a  b  c  d  e  f  g ]        커널 크기 3

stride 1:  [a b c] [b c d] [c d e] [d e f] [e f g]   → 출력 5칸
stride 2:  [a b c]         [c d e]         [e f g]   → 출력 3칸 (절반)
```

`Conv1`은 `strides = (2, 2)`라 가로세로 모두 절반이 되어 `224 → 112`.

**계산량** — stride 1이면 50,176개 위치, stride 2면 12,544개로 **1/4**. 이미지는 옆칸끼리 거의 비슷하니 다 계산해도 얻는 게 적다.

**근거 상태** — `확인됨`. `Conv1.strides` 실측.

**이해 상태** — `설명가능`. 이유(연산량)까지 스스로 말함.

## 0-D. 채널과 출력 채널 — 클래스 10개와 무슨 관계인가

**답변** — 채널은 **"이 위치에 대해 몇 가지를 기록하고 있는가"**다. 출력 채널은 각 층이 뱉어내는 결과물의 **가짓수**다(결과물 자체가 아니라).

```
Conv1의 결과물 자체 = 112 × 112 × 32 텐서 (숫자 401,408개)
그중 "32"가 채널    = 각 위치마다 몇 가지를 기록했나
```

**클래스 10개와의 관계** — 클래스 10개도 채널의 일종이다. 다만 **맨 마지막 층 하나만** 그렇다.

```
입력      Conv1     block들 …          Conv_1     GAP      Dense     logits
  3    →   32   →  16→24→32→…→320  →  1280   →  1280  →  1024   →   10
  ↑        ↑                            ↑                            ↑
RGB 3색  32가지 패턴                1280가지 특징              10개 클래스 점수
```

중간 층의 32니 1280이니 하는 숫자는 클래스와 아무 관계가 없다. 그냥 그 층에 커널을 몇 장 뒀는지다. **층의 출력**과 **모델의 출력**을 구분하면 정리된다.

**함께 정리된 표현** — "한 패치에 대해서 32가지 종류의 커널을 가져다 대겠다."

**근거 상태** — `확인됨`. 층별 shape는 `model.summary()` 실측.

**이해 상태** — `설명가능`.

## 0-E. 파라미터란 무엇인가 (핵심 교정)

**최초 이해** — "파라미터 = 커널을 가져다 댔을 때의 결과값". **이것이 틀렸다.**

**답변** — 파라미터는 **커널 안에 적혀 있는 숫자 그 자체**다. 계산 결과가 아니다.

```
  패치 (입력의 일부)          커널 (파라미터 27개)          결과값 1개
  ┌────────────────┐        ┌────────────────────┐
  │ 0.31  0.88 ... │        │ -0.1717 -0.2873 …  │
  │ 0.42  0.15 ... │   ×    │  0.2852  0.3873 …  │   →    -0.1677
  │ 0.77  0.03 ... │        │ -0.0997  0.0053 …  │
  └────────────────┘        └────────────────────┘
     이미지에서 옴              ↑ 이게 파라미터        ↑ 이건 파라미터 아님
```

**결정적 구분법 — "언제 변하나"**

| | 파라미터 (가중치) | 결과값 (출력) |
| --- | --- | --- |
| 정체 | 커널 **안에 적힌** 숫자 | 패치 × 커널 계산 **결과** |
| `Conv1`에서 개수 | **864개** | **401,408개** (112×112×32) |
| 다른 사진을 넣으면 | **안 변함** | 즉시 변함 |
| 학습을 돌리면 | **변함** | (파라미터가 변해서 따라 변함) |
| 어디 저장되나 | **`.keras` / `.tflite` 파일** | 저장 안 함, 계산하고 버림 |

마지막 줄이 제일 확실한 증거다. `.keras` 파일에는 이미지가 한 장도 안 들어있는데 파일 크기가 약 28MB다(715만 개 × 4바이트). 그 안에 든 것이 파라미터다.

**§6의 예시와 맞추면**

| | `몸무게 = w × 키 + b` | `Conv1` |
| --- | --- | --- |
| 파라미터 | **`w`, `b`** (2개) | **커널 안 숫자** (864개) |
| 입력 | 키 | 패치 |
| 출력 | 몸무게 | -0.1677 |

키를 180으로 바꾸면 출력은 변하지만 `w`, `b`는 그대로다.

**`Conv1`은 값이 아니라 층 이름이다.** `Conv` = convolution, `1` = 첫 번째. 패치 개수와 무관하다. MobileNetV2에서 이렇게 이름 붙은 층은 `Conv1`(맨 처음, 3→32)과 `Conv_1`(맨 마지막, 320→1280) 딱 둘뿐이고, 나머지 50여 개 층은 `block_1_expand` 식의 다른 이름을 쓴다.

**`Conv1` 커널의 864개 숫자는 어디서 왔나** — 우리가 계산한 값이 아니라 **다운로드한 값**이다. `keras.applications.MobileNetV2(weights="imagenet")` 한 줄이 구글이 ImageNet 120만 장으로 학습해둔 파일을 받아 커널에 채운다. `weights=None`(IR 백본)이면 그 자리를 난수로 채운다.

**근거 상태** — `확인됨`.

**이해 상태** — `설명가능`. 확인 질문("서로 다른 사진 두 장을 넣으면 864개는? 401,408개는?")에 정답.

## 0-F. 가중치 공유

**답변** — stride를 1로 바꿔도 `Conv1`의 파라미터 864개는 **그대로**다. 커널 수 32, 크기 3×3, 입력 채널 3이 전부 동일하기 때문이다.

```
stride 1 : 위치 50,176개에서 계산  ─┐
stride 2 : 위치 12,544개에서 계산  ─┼→ 전부 같은 커널 864개를 재사용
입력이 448×448 : 위치 4배          ─┘
```

**계산 횟수는 변하는데 파라미터 개수는 안 변한다.** 왼쪽 위 구석을 볼 때 쓴 커널과 오른쪽 아래를 볼 때 쓴 커널이 같은 커널이기 때문이다. 이것을 **가중치 공유(weight sharing)**라 한다.

Dense로 같은 입출력을 만들면:

| | 파라미터 |
| --- | --- |
| Conv1 (가중치 공유) | **864** |
| 같은 입출력을 Dense로 (150,528 → 401,408) | **약 604억** |

**7천만 배 차이**다. "가장자리를 찾는 법은 이미지 어느 구석에서나 똑같다"는 상식을 구조에 박아 넣은 결과이고, 이것 하나 때문에 CNN이 존재한다. 합성곱이 Dense와 다른 점 두 가지가 **지역성**(27개만 봄)과 **가중치 공유**다.

**근거 상태** — `확인됨`.

**이해 상태** — `설명가능`. 결론과 이유를 스스로 유도함.

## 0-G. logits

**답변** — 모델이 맨 마지막에 뱉는 숫자 10개. 클래스 하나당 하나씩, "이 사진이 이 클래스일 것 같은 점수".

```
logits = [ 2.0,  1.0,  0.5,  0.0, -0.5, -1.0, -1.0, -1.5, -2.0, -2.5 ]
           live  print display mask  ...
             ↑ 제일 높음 → 모델의 답은 "live"
```

- **확률이 아니다.** 다 더해도 1이 안 되고 음수도 나온다. 확률로 바꾸려면 softmax가 필요한데 **이 저장소는 계산하지 않는다** — `argmax`로 최댓값 위치만 찾는다(`tf_train.py:99`).
- **레이어 이름이기도 하다.** `tf_model.py:69`의 `layers.Dense(num_classes, name="logits")`.

**랜덤 상태여도 logits은 나온다.** 계산이 곱하고 더하는 것뿐이라 커널 안 숫자가 난수여도 똑같이 돈다. 실측: `weights=None` 백본에 무작위 이미지를 넣으면 특징 첫 값이 `3.2e-14`(사실상 0), ImageNet 가중치면 같은 자리가 `0.008342`이고 1280개 중 687개가 0보다 컸다.

## 3. 정규화의 MEAN과 STD는 무엇이 다른가

**답변** — 공식은 하나다.

```
x_norm = (x - MEAN) / STD
```

- **MEAN(뺄셈)** : 위치 이동. 중심을 0으로. → 0점 조정
- **STD(나눗셈)** : 크기 조절. 퍼짐을 1로. → 눈금 간격 조정

IR의 경우 숫자로 보면:

```
원본 픽셀    0 ────── 128 ────── 255
÷255       0.0 ───── 0.5 ────── 1.0
-MEAN(0.5) -0.5 ──── 0.0 ────── +0.5   ← 중심 이동
÷STD(0.5)  -1.0 ──── 0.0 ────── +1.0   ← 폭 2배
```

MEAN만 있으면 `[-0.5, 0.5]`에 머물고, STD만 있으면 `[0, 2]`로 치우친다. 둘 다 있어야 `[-1, 1]`이 나온다.

**왜 정규화하나** — 0~255를 그대로 넣으면 값이 크고 한쪽으로 쏠려 학습이 불안정하다. 평균 0, 표준편차 1 근처로 맞춘다.

**RGB와 IR의 값이 다른 이유**

| | 값 | 성격 |
| --- | --- | --- |
| RGB | `[0.485, 0.456, 0.406]` / `[0.229, 0.224, 0.225]` | ImageNet 120만 장의 **실제 채널별 통계**. 업계 표준값 |
| IR | `[0.5]` / `[0.5]` | 통계가 아니라 **범위 변환 공식**. `(x-0.5)/0.5 = 2x-1`, 즉 `[0,1]` → `[-1,1]` |

IR에 대응하는 ImageNet 통계가 없으므로 대칭 범위로 보낸 것이고, 이는 MobileNetV2 원래 전처리 범위와 일치한다.

**코드** — `spec.py:9-12`, 적용은 `tf_dataset.py:52-57`

## 4. 어떤 값이 어떤 정규화를 거쳐 어디로 가는가 (전체 흐름)

**질문** — 값의 흐름이 머릿속에서 안 잡힌다.

**답변** — 픽셀 값 200 하나를 끝까지 추적하면 명확해진다.

```
                    [ 디스크 / 카메라 ]
                     RGB 200    IR 200
                        │          │
        ┌───────────────┴──┐    ┌──┴────────────┐
        │  ÷ 255  → 0.78431│    │ ÷255 → 0.78431│
        │ (x-0.485)/0.229  │    │  (x-0.5)/0.5  │  ← 여기서 갈라짐
        │        → 1.30705 │    │      → 0.56863│
        └────────┬─────────┘    └───────┬───────┘
    ═════════════╪══════════════════════╪══════════  ◀ 모델 경계 (.tflite 시작)
            입력 a_rgb              입력 b_ir
             1.30705                 0.56863
                 │                      │
        ┌────────┴─────────┐            │
        │ Lambda 보정      │            │  (Lambda 없음)
        │ ×0.229 +0.485    │            │
        │   → 0.78431 (원상복구)        │
        │ ×2 -1 → 0.56863  │            │
        └────────┬─────────┘            │
                 ▼                      ▼
          RGB 백본 0.56863        IR 백본 0.56863   ← 같은 값
                 │                      │
            1280차원 특징           1280차원 특징
                 └──────── concat ──────┘
                        2560차원 → 헤드 → logits 10개
```

여기서 알아야 할 것 세 가지.

**① RGB는 정규화했다가 되돌린다.** Lambda가 `×0.229 +0.485`로 정확히 `0.78431`을 복구한다. 수학적으로는 낭비다.

**② 그 낭비의 이유는 모델 경계다.** `.tflite`는 이중선 아래만 담는다. 위쪽 전처리는 학습 때 `tf_dataset.py`가, 추론 때 **Android 앱**이 담당한다. 앱이 이미 "ImageNet 정규화해서 넣는다"는 계약으로 배포되어 있고 백본은 `[-1,1]`을 원하므로, **앱을 안 건드리려고 보정을 모델 안으로 넣었다.**

**③ 두 백본이 같은 값을 본다.** 이것이 conv1 `sum` 전략의 전제다(§8 참고).

**코드** — `tf_dataset.py:52-57`, `tf_model.py:73-79`, `tf_model.py:102-105`

**근거 상태** — `확인됨`.

**이해 상태** — `읽으면 알겠음`. 다만 이 절이 **학습 방식의 근거**다 — 픽셀 하나를 숫자로 추적한 뒤에야 잡혔고, 말로만 설명들을 때는 안 잡혔다. 이후 모든 항목에 같은 방식(값 하나를 끝까지 계산해 코드 출력과 대조)을 적용한다.

**리뷰 메모** — RGB의 왕복 변환은 수학적으로 제거 가능하다. 앱이 `/255` 후 `×2-1`로 보내면 Lambda와 ImageNet 상수가 통째로 사라진다. 다만 앱·PyTorch 파이프라인·검증된 모델이 얽혀 있어 지금 건드릴 사안이 아니다. "왜 이렇게 생겼는지 아는 상태"로 남긴다.

**답변** — `모델종류 → (입력이름, shape)` 딕셔너리. shape는 `(높이, 너비, 채널)`이고 배치 차원은 빠져 있다.

2. `model_signature.py` — 변환 전 Keras와 변환 후 TFLite를 같은 규격으로 **검증** (`tflite=True` 플래그로 함수 재사용)
3. Android 앱 — 이 이름으로 텐서 **바인딩**

1·2는 `spec.py` 하나를 고치면 따라오지만 3은 사람이 맞춰야 한다. 즉 **이 파일은 앱과의 계약서**이며, 수정은 앱 수정을 동반한다.

## 6. 가중치란 무엇인가

**답변** — 모델이 학습으로 찾아낸 숫자들.

| `logits` | 1024 × 10 + 10 | 10,250 |
| **헤드 합계** | | **2,632,714** |
| RGB 백본 (3채널) | | 2,257,984 |

| | 무엇 | 어디 |
| --- | --- | --- |
| 구조(architecture) | 뼈대. 레이어를 어떻게 쌓는가 | `tf_model.py` 코드 |
| 가중치(weights) | 내용물. 715만 개의 숫자 | `.keras` / `.tflite` 파일 |

`tf_model.py`를 실행하면 구조는 즉시 생기지만 가중치는 의미 없는 랜덤값이다. 학습해야 쓸모 있어진다.

**용어 주의** — 머신러닝에서 **데이터**는 입력(이미지·라벨)을 뜻한다. 모델 내부 숫자는 **파라미터** 또는 **가중치**라 부른다.

## 7. 백본과 헤드란 무엇인가

**답변** — 신경망은 두 부분으로 나뉜다.

```
   이미지                  특징 벡터              답
224×224×3 ──[ 백본 ]──▶ 1280개 숫자 ──[ 헤드 ]──▶ 10개 점수
=150,528개
```

- **백본** : 이미지에 무엇이 있는지를 1280개 숫자로 압축. 앞 레이어는 단순한 것(선·색 경계), 뒤로 갈수록 복잡한 것(무늬·재질)을 본다.
- **헤드** : 그 요약을 받아 "답이 무엇인가"를 낸다.

**왜 나누나** — 백본은 문제와 무관하고, 헤드는 문제에 종속적이기 때문이다. "가장자리를 찾는 법"은 개/고양이를 분류하든 스푸핑을 잡든 똑같이 필요하지만, "이 특징이면 live다"는 이 프로젝트에만 필요하다. 그래서 백본은 남이 학습한 것을 가져다 쓰고 헤드만 새로 만든다.

```python
keras.applications.MobileNetV2(
    include_top=False,   # "머리는 빼고 몸통만"
    weights="imagenet",  # "ImageNet으로 학습된 숫자로 채워서"
    pooling="avg",
)
```

`include_top=False`가 없으면 ImageNet용 1000클래스 헤드가 딸려온다. 우리는 10클래스가 필요하므로 몸통만 받아 우리 헤드를 붙인다.

**코드** — 백본 `tf_model.py:107-120`, 헤드 `tf_model.py:56-70`

**근거 상태** — `확인됨`.

**이해 상태** — `읽으면 알겠음`. 최초 이해에 오해 두 가지가 있었고 교정됨.

| 최초 이해 | 교정 |
| --- | --- |
| "백본 = 이미 학습된 백그라운드 모델" | `backbone`은 **등뼈**(background 아님). 그리고 **"이미 학습된"은 정의가 아니다** — 백본은 역할 이름이고, 안의 가중치가 사전학습인지 랜덤인지는 별개다. 실제로 `ir_backbone`은 `weights=None`, 즉 랜덤으로 태어난다(`tf_model.py:117`) |
| "헤드 = 내가 받고 싶은 결과(10클래스)" | 헤드는 **결과가 아니라 결과를 만드는 레이어들**이다. 결과는 그 출력인 logits |

**추가로 중요한 사실** — 저장소 전체를 검색한 결과 `trainable=False`가 **어디에도 없다.** 즉 학습을 돌리면 **백본의 가중치도 계속 바뀐다.** ImageNet 가중치는 고정된 최종값이 아니라 **좋은 출발점**이다. 이를 **미세조정(fine-tuning)**이라 한다. `tf_train.py:137`의 학습률이 `1e-4`로 작은 이유가 이것이다 — 가져온 가중치가 초반에 망가지지 않도록 조심스럽게 움직인다. 밑바닥부터 학습이면 보통 `1e-3`을 쓴다.

## 8. conv1의 `mean`과 `sum`은 무엇이고, 정규화와 무슨 관계인가

**답변** — 별개 장치지만 하나라도 어긋나면 나머지가 무의미해지는 세트다.

- **정규화 MEAN/STD** : **입력 데이터**를 건드린다
- **conv1 reduction** : **커널 가중치**를 건드린다

**왜 reduction이 필요한가** — MobileNetV2의 Conv1 커널은 `(3,3,3,32)`, 즉 입력 채널 3개다. IR은 1채널이라 `(3,3,1,32)`로 줄여야 한다. 합성곱 출력은 세 채널 기여의 **합**이므로:

```
out = k_R * x_R + k_G * x_G + k_B * x_B
```

흑백을 3채널 복제해 넣었다면 `out = (k_R + k_G + k_B) * x`. 따라서 **원본과 같은 출력을 내려면 `sum`(더하기)이어야 한다.** `mean`은 3으로 나눈 값이 되어 **출력이 정확히 1/3로 줄어든다.**

**1/3이 왜 문제인가** — 가중치 이식 함수는 Conv1만이 아니라 **BatchNorm의 통계값도 그대로 복사**한다(`tf_model.py:42-46`의 shape 일치 검사를 BN의 gamma/beta/moving_mean/moving_variance가 통과). 그 통계는 "Conv1이 원래 크기로 출력한다"는 전제로 계산된 값이다. Conv1 출력만 1/3이 되면 BN이 기대하는 분포와 어긋나 사전학습의 이점이 상당 부분 사라진다.

**정규화와의 연결** — `sum`이 "원본과 동일"하다는 등식은 **IR 입력 범위가 원본 Conv1이 보던 범위와 같아야** 성립한다. 그 전제를 만드는 것이 정규화다.

```
IR_MEAN/IR_STD (0.5/0.5)          → IR을 [-1,1]로
_rgb_current_norm_to_mobilenet_range → RGB도 [-1,1]로
MobileNetV2 ImageNet 학습 범위       → [-1,1]
```

세 개가 전부 `[-1,1]`로 정렬되어 있다. `IR_MEAN/IR_STD`를 바꾸면 conv1 전략까지 다시 봐야 한다.

**검증** — `tests/model/test_conv1_reduction.py`가 이를 수치로 고정한다. 테스트 입력이 `np.random.uniform(-1.0, 1.0, ...)`인 것도 위 전제의 재현이다.

- `sum` 출력 == 원본 RGB 출력 (허용 오차 `1e-5`)
- `mean` 출력 == 원본 RGB 출력 ÷ 3

**코드** — `tf_model.py:17-49`, 테스트 `tests/model/test_conv1_reduction.py`

**근거 상태** — `확인됨` / `기록됨`. 위키 `roadmap/complete-overhaul-backlog` P0-08과 `log.md` 07-22행에 `sum` 채택 결정이 있고, 저장소 `AGENTS.md`가 `sum`을 강제한다.

**이해 상태** — `읽으면 알겠음`. 축소가 커널 shape의 **3번째 자리**에서 일어난다는 것은 [[0-B]]에서 `설명가능`.

**⚠️ 리뷰에서 발견된 결함 (2026-08-10 해소됨)** — `sum` 채택 이후에도 **기본값이 전부 `mean`으로 남아 있었다.** 위키 명령어 SSOT의 예시도 플래그를 빠뜨리고 있어서, **문서대로 실행하면 기각된 `mean`으로 학습되고 아무것도 경고하지 않는 상태**였다.

같은 날 다섯 곳 전부 `sum`으로 바꿨다.

| 위치 | 변경 전 → 후 |
| --- | --- |
| `scripts/keras/run_fixed_split.sh:14` | `REDUCTION="mean"` → `"sum"` |
| `keras_pipeline/tf_train.py` argparse | `"mean"` → `"sum"` |
| `keras_pipeline/tf_model.py` argparse | `"mean"` → `"sum"` |
| `build_dual_mobilenetv2()` 시그니처 | `"mean"` → `"sum"` |
| `build_single_mobilenetv2()` 시그니처 | `"mean"` → `"sum"` |

처음 발견 때는 앞의 세 곳만 봤는데, 고치면서 함수 시그니처 기본값 두 곳이 더 있는 것을 확인했다. argparse를 안 거치는 호출은 그쪽을 탄다. `run_all_folds.sh`는 플래그를 안 넘기므로 이제 파서 기본값을 통해 `sum`을 받는다. `AGENTS.md`와 위키 명령어 가이드의 "기본값은 `sum`이 아니다"라는 문장도 같은 세션에 다시 썼다.

**남은 것** — `ast.parse`와 `bash -n`으로만 확인했고 실제 학습으로는 검증하지 않았다. 그리고 **기본값을 고정하는 테스트가 없다** — `test_conv1_reduction.py`는 두 값을 명시적으로 넘기므로 기본값이 다시 `mean`으로 돌아가도 못 잡는다. `crop_rgb`는 IR 백본이 없어 영향 없음. 위키 `issues/needs-verification` 항목 15.

## 9. 백본 동결(freeze)이란 `trainable=False`를 말하는가

**답변** — 그렇다. 학습 한 스텝은 ① 순전파 ② 손실 계산 ③ 역전파(가중치 수정)인데, `trainable=False`는 **③에서 그 레이어를 건너뛰라**는 뜻이다. ①②는 그대로다. "계속 일하되 배우지는 마라".

| | 동결 (`False`) | 전체 학습 (`True`, 현재) |
| --- | --- | --- |
| 학습 대상 | 263만 (헤드만) | 715만 |
| 속도·메모리 | 빠름 | 느림 |
| 데이터 적을 때 | 과적합 방지에 유리 | 백본이 망가질 위험 |
| 도메인 차이 클 때 | ImageNet 특징만으론 한계 | 적응 가능 |

**현재 선택의 타당성** — IR 스푸핑은 ImageNet(일반 컬러 사진)과 먼 문제다. "인쇄물의 미세 질감", "화면의 모아레" 같은 특징은 ImageNet에 없으므로 백본까지 적응시키는 전체 학습이 합리적이다. 특히 IR 백본은 이식된 가중치라 완벽하지 않아 동결하면 손해다.

**흔한 2단계 전략** — 1단계에서 백본 동결 후 헤드만 학습(랜덤 헤드의 엉터리 그래디언트가 백본으로 역류하는 것을 방지), 2단계에서 동결 해제 후 전체 미세조정. 현재 코드는 이 대신 **처음부터 학습률을 낮게(1e-4)** 잡아 완화하고 있다. 유효한 대안이다.

**⚠️ 함정 — BatchNorm** — Keras에서 `trainable=False`는 BatchNorm에 한해 의미가 하나 더 있다. 가중치 갱신 중단에 더해 **추론 모드로 전환**되어 저장된 이동평균을 쓴다. 이 모델은 IR 백본에 **ImageNet의 BN 통계를 복사**해 넣었는데(§8), IR의 실제 분포는 그와 다르다.

- 현재(동결 안 함) : BN이 IR 데이터로 통계를 다시 학습 → 맞춰짐
- 동결한다면 : ImageNet 통계에 고정 → IR에 안 맞는 채로 굳음

**즉 현재 구조에서 백본 동결은 오히려 위험하다.** 이식 전략과 동결 전략이 얽혀 있다.

**근거 상태** — `확인됨`. 위키 `issues/needs-verification` 항목 9에 `--trainable` 옵션 도입 제안이 이미 등록되어 있다.

**이해 상태** — `읽으면 알겠음`. 이 절은 **역전파([[0-H]])를 전제**하므로 그것을 먼저 채워야 재점검이 의미 있다.

**리뷰 메모** — 동결하지 않은 것은 타당한 선택이지만, 코드에 의도가 적혀 있지 않아 "일부러 안 한 것"인지 "생각을 안 한 것"인지 구분되지 않는다.

## 10. 이 프로젝트에 ImageNet을 쓰는 것이 맞는가

**답변** — 맞다. 그리고 이는 추정이 아니라 **자사 데이터로 검증된 결과**다.

**도움이 되는 부분** — 앞쪽 레이어다. 초반 합성곱이 배우는 가장자리·밝기 변화·질감 필터는 문제와 무관하게 필요하고, 안티스푸핑은 상당 부분 질감 문제다. 의료영상·위성사진처럼 먼 도메인에서도 ImageNet 초기화가 랜덤보다 낫다는 것은 견고하게 확인된 사실이다.

**궁합이 나쁜 부분**

1. **추상화 수준 차이** — ImageNet은 "무슨 물체인가"를 배웠고 뒤쪽 레이어일수록 물체 의미를 인코딩한다. 안티스푸핑은 "이 표면이 진짜인가"를 묻는다. 물체는 이미 다 얼굴이다. 따라서 **가치는 백본 앞쪽에 몰려 있다.**
2. **불변성 방향** — ImageNet은 조명·색감·대비에 **둔감하게** 만든다. 안티스푸핑은 그 정보가 필요하다. `미확인` — 이 상충이 실제로 성능에 영향을 주는지는 측정된 바 없다.
3. **IR에는 해당 없음** — ImageNet에 적외선은 없다. 이식은 "랜덤보다 낫다" 수준이다.

**대안 검토 결과 (`기록됨`)** — 얼굴인식 사전학습(MS1M-V2, `face_mobilenetv2_mcp.weights.h5`)을 2026-07-07에 실제로 이식해 30에폭 평가했고, **기각되었다.**

| | val_acc | ACER |
| --- | --- | --- |
| 얼굴 사전학습 | 94.29% | 3.84% (APCER 4.88 / BPCER 2.80) |
| ImageNet 기준선 | 99.71% | 0.60% |
| 제품 통과 기준 | | ≤ 2.0% |

**기각 원인은 PReLU 불일치**다. 원본 PyTorch 가중치에 표준 MobileNetV2에 없는 PReLU alpha 파라미터가 다수 있었고, ReLU6 기반 Keras 구조로 이식하면서 활성 컷오프 분포가 왜곡되었다. 더해서 PReLU는 NNAPI 미지원이라 CPU fallback을 유발하는 **배포 차단 요인**이기도 하다. 정확도만의 문제가 아니었다.

## 11. 학습 한 스텝은 실제로 무엇을 하는가

**답변** — `model.fit`이 도는 동안 반복되는 단위는 **스텝(step)** 이고, 한 스텝은 이것뿐이다.

```
배치 8장 ─▶ 순전파 ─▶ logits (8, 10) ─▶ 손실 1개 숫자
                                          │
                          역전파 ◀────────┘
                             │
                  Adam이 715만 파라미터를 조금씩 수정
```

`steps_per_epoch = ceil(len(train_items) / 8)`이고, 1에폭은 학습 데이터를 한 바퀴 도는 것이다. `.repeat()`이 붙어 있지만 `steps_per_epoch`가 정확히 한 바퀴 분량이라 에폭 경계와 데이터 경계는 일치한다. 다만 `reshuffle_each_iteration=True`라 **순서는 에폭마다 바뀐다** — 증강이 에폭마다 안 바뀌는 것(항목 14)과는 별개 문제다.

### logits에서 손실이 나오는 과정

모델 출력은 확률이 아니라 **logits**, 즉 softmax 이전의 날 점수 10개다([[0-G]]). `from_logits=True`가 이 뜻이다.

logits이 `[2.0, 1.0, 0.5, 0.0, -0.5, -1.0, -1.0, -1.5, -2.0, -2.5]`이고 정답이 `live`(0)라면:

| 단계 | 값 |
| --- | --- |
| softmax | `0.5082, 0.1870, 0.1134, 0.0688, 0.0417, 0.0253, 0.0253, 0.0153, 0.0093, 0.0056` |
| 정답 확률 | `0.5082` |
| 손실 `-log(0.5082)` | **`0.6768`** |

교차 엔트로피는 결국 **정답에 준 확률의 음의 로그**다. 확률 1.0을 주면 0, 0에 가까우면 무한대로 커진다.

### label smoothing이 바꾸는 것

기본값이 `0.1`이다. 정답 라벨을 1.0/0.0의 극단이 아니라 완만하게 만든다.

```
target = one_hot × (1 - 0.1) + 0.1 / 10
       → live: 0.91,  나머지 9개: 각 0.01
```

같은 logits에 대해:

| | hard 라벨 | smoothing 0.1 |
| --- | --- | --- |
| 위 예시(정답 확률 0.5082) | `0.6768` | **`0.9268`** |
| 완벽한 확신(정답 확률 ≈ 1.0) | `0.0` | **`3.6`** |

두 번째 줄이 핵심이다. **smoothing은 "확신"을 벌한다.** hard 라벨에서는 100% 확신하면 손실이 0이라 더 배울 게 없지만, smoothing에서는 오히려 3.6이라는 큰 손실이 된다.

**⚠️ 학습 곡선 해석 주의** — smoothing이 켜져 있으면 **훈련 손실은 0으로 수렴하지 않는다.** 예측이 목표 분포(`0.91 / 0.01×9`)와 정확히 같아졌을 때의 손실이 이론적 바닥이고, 그 값은 **`0.5003`** 이다. 학습곡선이 0.5 부근에서 평평해지는 것은 정상이며 학습이 멈춘 신호가 아니다. `--label-smoothing 0` 실행과 손실 값을 직접 비교해서도 안 된다 — **바닥이 다른 두 자를 대는 것**과 같다. 비교하려면 손실이 아니라 `acc`와 ACER를 봐야 한다(`SparseCategoricalAccuracy`는 argmax만 보므로 smoothing과 무관).

**구현 메모** — `label_smoothing`을 쓰는 `CategoricalCrossentropy`는 one-hot 라벨을 요구하는데 데이터셋 라벨은 정수 하나다. 그래서 `loss_fn`이 `reshape(-1)` → `one_hot` → 호출로 감싼다. 기능 추가가 아니라 **규격 변환 어댑터**다.

### Adam과 학습률 1e-4

학습률을 "그래디언트에 곱하는 상수"로만 보면 실제 이동 폭을 알 수 없다. 그래디언트 크기가 레이어마다 천차만별이기 때문이다. Adam은 파라미터마다 **최근 그래디언트 크기로 나눠서** 그 편차를 없앤다. 결과적으로 한 스텝의 이동량이 대략 학습률 크기가 된다.

> `lr = 1e-4` ≈ "파라미터 하나가 한 스텝에 약 ±0.0001 움직인다"

§7에서 "사전학습 가중치가 망가지지 않게 작게 잡았다"고 한 말이 여기서 숫자로 이어진다. 밑바닥 학습의 관례값 `1e-3`이면 한 스텝 이동이 10배가 된다.

### CosineDecay — 학습률이 고정이 아니다

`1e-4`는 **시작값**이다. 코사인 곡선을 따라 `alpha=0.01`, 즉 시작값의 1%인 `1e-6`까지 떨어진다. `--epochs 10` 기준:

| 에폭 종료 | 학습률 | 시작 대비 |
| --- | --- | --- |
| 0 (시작) | `1.00e-04` | 100% |
| 2 | `9.06e-05` | 91% |
| 5 | `5.05e-05` | 51% |
| 7 | `2.14e-05` | 21% |
| 9 | `3.42e-06` | 3% |
| 10 (종료) | `1.00e-06` | 1% |

초반은 거의 안 줄고 중반에 급히 떨어진다. 이 표는 데이터 개수와 무관하다 — `decay_steps = epochs × steps_per_epoch`이므로 데이터가 늘면 스텝도 같이 늘어 에폭 기준 곡선은 동일하다.

**⚠️ `--epochs`는 길이 옵션이 아니라 스케줄 옵션이다** — `--epochs 20`으로 바꾸면 총 스텝이 2배가 되어 **10에폭 시점의 학습률이 위 표의 값이 아니게 된다.** 따라서 (a) 중단한 학습을 에폭만 늘려 이어 붙일 수 없고, (b) 에폭 수가 다른 두 실험은 학습률 궤적이 달라 공정한 비교가 아니다.

## 12. APCER · BPCER · ACER는 정확히 무엇인가

**질문** — ACER, APCER, BPCER이 정확히 뭔가?

**답변** — 출발점은 **학습은 10클래스지만 평가는 2클래스로 접는다**는 것이다.

```python
live_mask  = labels == 0      # live만 진짜
spoof_mask = labels != 0      # 1~9는 전부 하나의 "공격"으로 취급
```

그 위에서 두 종류의 오류를 **각각의 분모로** 나눈다. 이게 핵심이다.

| | 무엇을 세나 | 분모 | 현장에서의 의미 |
| --- | --- | --- | --- |
| **APCER** | 스푸핑인데 `live`라고 답한 수 | 전체 **스푸핑** 수 | **뚫린 비율** (보안 실패) |
| **BPCER** | live인데 스푸핑이라 답한 수 | 전체 **live** 수 | **거부당한 비율** (사용성 실패) |
| **ACER** | 위 둘의 **평균** | — | 한 숫자로 요약한 값 |

가상의 validation 결과 하나로 끝까지 계산하면:

```
live  200장 중  6장을 스푸핑이라 거부  → BPCER = 6/200  = 3.00%
spoof 900장 중 46장을 live라고 통과   → APCER = 46/900 = 5.11%

ACER = (5.11% + 3.00%) / 2 = 4.06%
```

**왜 정확도를 안 쓰나** — 같은 결과의 정확도는 **95.27%**(1048/1100)인데 ACER는 4.06%로 제품 기준 2.0%를 못 넘긴다. 10클래스 중 9개가 스푸핑이라 데이터가 기울어 있어서, live가 전체의 18%뿐이다. live를 전부 틀려도 정확도는 82%가 나온다. 정확도는 다수 클래스에 묻히지만 APCER/BPCER는 분모가 따로라 그 은폐가 불가능하다.

그리고 두 오류는 **의미가 다르다.** 뚫리는 것은 보안 사고고 거부되는 것은 사용자 불편이다. 하나로 뭉친 정확도는 둘을 구분 못 한다.

**⚠️ 이 코드의 APCER는 표준 정의와 다르다** — `utils.py:393`은 스푸핑 9종을 **한 분모에 몰아서** 나눈다. ISO/IEC 30107-3의 APCER는 **공격 종류별로 계산한 뒤 그중 최악값**을 쓴다. 위 예시를 종류별로 보면:

```
curved_print    15.00%   ← 최악
curved_picture  12.00%
curved_mask      8.00%
...
mask             0.00%

이 코드 (합산)    APCER =  5.11%  →  ACER = 4.06%
ISO   (최악 기준) APCER = 15.00%  →  ACER = 9.00%
```

**공격자는 평균으로 공격하지 않고 제일 잘 통하는 방법으로 공격한다.** `curved_print`가 15% 뚫리는데 전체 평균이 5%라 괜찮아 보이는 상황이 실제로 가능하다. curved 4종이 추가되어 종류가 9개가 된 지금은 희석 효과가 더 크다.

다만 `on_epoch_end`가 클래스별 recall을 매 에폭 출력하므로 종류별 취약점은 **로그에는 보인다** — 단지 ACER 숫자에 반영되지 않을 뿐이다. 체크포인트 선택은 그 ACER로 하므로, 특정 공격에만 취약한 모델이 선택될 여지가 있다.

**코드** — `utils.py:386-395`(계산), `tf_train.py:96-104`(출력)

**근거 상태** — `확인됨`.

**이해 상태** — `모름` (미기입). 역전파와 무관한 절이라 0-H와 독립적으로 재점검할 수 있다.

## 13. validation loss는 무엇이고, 왜 이 파이프라인엔 없는가

**질문** — validation_loss는 또 뭔가?

**답변** — 훈련 손실과 **똑같은 공식을 검증셋에 적용한 값**이다. 차이는 그 데이터로 가중치를 수정하지 않는다는 것뿐이다.

쓸모는 하나로 요약된다 — **과적합 감지**.

```
train loss ↓ , val loss ↓   →  잘 배우는 중
train loss ↓ , val loss ↑   →  과적합 (외우기 시작)
```

훈련 손실만 보면 이 둘이 구분되지 않는다. 계속 내려가니까. 검증 손실이 **돌아서 올라가는 시점**이 "여기서 멈춰야 한다"는 신호다.

**그런데 이 파이프라인에는 없다.** `model.fit`에 `validation_data`가 전달되지 않아서, `history.history`에는 `loss`와 `acc` — 둘 다 **훈련** 데이터 기준 — 만 있다. 검증셋은 `AcerCheckpoint`가 `predict`로 따로 돌려 **ACER만** 뽑아 쓴다. 손실은 계산하지 않는다.

지금 그 자리를 대신하는 건 **에폭별 val ACER**다(학습곡선 PNG의 `1-ACER` 곡선). ACER가 개선을 멈추고 나빠지면 그것도 과적합 신호이긴 하다. 다만 ACER는 argmax만 보는 계단식 지표라 **손실보다 둔하다** — 확신도가 0.99에서 0.51로 떨어져도 답이 맞으면 ACER는 그대로지만 손실은 즉시 반응한다.

**연결** — label smoothing A/B에서 off를 "과적합처럼 보인다"고 판단한 근거가 단말 추론 결과의 등락이었는데, val loss는 바로 그 판단을 **학습 중에** 숫자로 보여주는 계기판이다. 지금은 그게 없어서 단말까지 내보낸 뒤에야 눈으로 확인하게 된다.

**추가할지는 별개 문제다** — `validation_data=val_ds`를 넘기면 에폭마다 검증셋을 한 번 더 통과시켜야 하는데, `AcerCheckpoint`가 이미 같은 데이터로 `predict`를 돌리고 있어 **검증 연산이 두 배**가 된다.

**코드** — `tf_train.py:232-237`(fit), `85-120`(대신 쓰이는 ACER 콜백)

**근거 상태** — `확인됨`.

**이해 상태** — `모름` (미기입). 손실과 과적합을 전제하므로 0-H 이후에 본다.

### 여기서 나온 리뷰 논점 세 가지

**① softmax가 없어서 앱은 확률을 못 받는다.** argmax는 단조 변환에 불변이라 softmax를 통과시켜도 결과가 같으므로 계산할 이유가 없다. 다만 임계값 판정("live 확률 0.9 이상만 통과")을 하려면 앱이 직접 계산해야 한다. 위키 항목 19(안드로이드 전처리 계약)와 같이 볼 사안.

**② Flatten이 아니라 Reshape다.** 교과서 CNN의 Flatten은 `(7,7,1280)` 62,720개를 한 줄로 펴는 것인데, GAP이 이미 1280으로 줄여놨다. 파라미터 차이가 큰 이유이기도 하다 — Flatten 후 1024로 가면 `62720 × 1024 = 6,422만`, GAP 후면 `1280 × 1024 = 131만`으로 **약 49배**.

**③ max pooling이 한 곳도 없다.** 다운샘플링을 전부 stride 2 합성곱이 한다. 이 프로젝트에서 pooling은 크기 줄이기용이 아니라 **맨 마지막 GAP 하나**뿐이다.
